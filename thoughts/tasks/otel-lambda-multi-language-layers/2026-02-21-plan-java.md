# Java Lambda OTel Layer Testing Implementation Plan

## Overview

Replace the Node.js Lambda functions and build pipeline with Java equivalents on a dedicated branch, using **two different** OpenTelemetry Java instrumentation approaches — **javaagent** (auto-instrumentation via bytecode agent) and **javawrapper** (handler class substitution) — one per Lambda, to verify both layer types in a single deployment.

## Current State Analysis

The project deploys two Node.js Lambda functions behind API Gateway REST APIs, instrumented with OTel via Lambda layers:
- **Launch Lambda** (`requestLaunchLambda.ts`) — receives POST, calls Mission Control API via HTTP, returns launch status
- **Mission Lambda** (`controlMissionLambda.ts`) — receives GET with path param, reads/writes DynamoDB, returns mission progress

Both use a reusable Terraform module (`infrastructure/modules/otel-lambda/`) that wires a Lambda with instrumentation + collector layers. The module has Node.js-specific config: `runtime = "nodejs22.x"`, `OTEL_NODE_ENABLED_INSTRUMENTATIONS`, and default layer ARN pointing to the Node.js layer.

### Key Discoveries:
- Module already accepts `instrumentation_layer_arn` and `extra_env_vars` as variables, allowing per-lambda layer/env customization (`infrastructure/modules/otel-lambda/variables.tf:22-31`)
- `merge()` in the module's environment block (`infrastructure/modules/otel-lambda/main.tf:45-58`) means `extra_env_vars` can override hardcoded defaults like `AWS_LAMBDA_EXEC_WRAPPER`
- OpenAPI specs (`src/launch/openapi.json`, `src/mission/openapi.json`) are language-agnostic — only contain API shape + Lambda ARN template vars
- Collector config (`collector.yaml`) is language-agnostic
- API Gateway, DynamoDB, and test infrastructure require no changes

## Desired End State

A deployable Java branch where:
1. **Launch Lambda** uses the **javaagent** layer (bytecode auto-instrumentation of `java.net.http.HttpClient`)
2. **Mission Lambda** uses the **javawrapper** layer (handler substitution with AWS SDK v2 DynamoDB auto-instrumented via SPI)
3. Both produce OTel traces that appear in the configured backend
4. A distributed trace links Launch → (HTTP) → API Gateway → Mission → DynamoDB
5. The Mission Lambda uses `/opt/otel-proxy-handler` to extract trace context from API Gateway v1 headers, enabling proper parent-child trace linking

### Verification:
- `./gradlew build` succeeds, producing two deployment ZIPs
- `terraform apply` deploys both lambdas with their respective layers
- `curl POST /launch` triggers Launch → Mission call chain
- Traces appear in the observability backend with:
  - Launch Lambda span with child HTTP client span (javaagent)
  - Mission Lambda span with child DynamoDB spans (javawrapper)
  - Both linked in a single distributed trace

## What We're NOT Doing

- Parameterizing the `otel-lambda` module for multi-language support (just modifying directly for Java on this branch)
- Building the Java layers from source (user handles layer acquisition separately)
- Adding unit tests (this is a proof-of-concept for layer testing)
- Supporting both Java and Node.js simultaneously on the same branch
- Changing the API Gateway setup, DynamoDB table, or OpenAPI specs

## Implementation Approach

The two Java layer types require different Lambda layers but the handler code is identical in structure — both are plain `RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent>` POJOs. Neither requires OTel dependencies in the handler code. The key differences are:
- **javaagent**: Bytecode instrumentation via `-javaagent` JVM flag (set automatically by layer wrapper script). Instruments everything on the classpath including `java.net.http.HttpClient`.
- **javawrapper**: Shell-script handler class substitution. Instruments AWS SDK v2 via SPI. For API Gateway triggers, `/opt/otel-proxy-handler` extracts trace context from request headers.

Both use shadow JARs (fat JARs) packaged into deployment ZIPs alongside `collector.yaml`. The javaagent Lambda gets `OTEL_JAVA_AGENT_FAST_STARTUP_ENABLED=true` to reduce cold start.

#### 1.3 Create Java Handler: Launch Lambda (javaagent)

**File**: `launch/src/main/java/com/example/launch/RequestLaunchHandler.java` (new)

```java
package com.example.launch;

import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import com.amazonaws.services.lambda.runtime.events.APIGatewayProxyRequestEvent;
import com.amazonaws.services.lambda.runtime.events.APIGatewayProxyResponseEvent;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.node.ObjectNode;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class RequestLaunchHandler implements RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> {

    private static final ObjectMapper mapper = new ObjectMapper();
    private static final HttpClient httpClient = HttpClient.newHttpClient();

    @Override
    public APIGatewayProxyResponseEvent handleRequest(APIGatewayProxyRequestEvent event, Context context) {
        try {
            JsonNode body = mapper.readTree(event.getBody());
            String rocketName = body.get("rocketName").asText();
            String destination = body.get("destination").asText();

            String missionControlBaseUrl = System.getenv("MISSION_CONTROL_BASE_URL");
            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create(missionControlBaseUrl + "/mission/" + rocketName))
                    .GET()
                    .build();

            HttpResponse<String> response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
            JsonNode mission = mapper.readTree(response.body());
            int progress = mission.get("progress").asInt();
            String status = progress > 0 ? "UNDERWAY" : "LAUNCHING";

            ObjectNode result = mapper.createObjectNode();
            result.put("rocketName", rocketName);
            result.put("destination", destination);
            result.put("status", status);

            return new APIGatewayProxyResponseEvent()
                    .withStatusCode(200)
                    .withBody(mapper.writeValueAsString(result));
        } catch (Exception e) {
            return new APIGatewayProxyResponseEvent()
                    .withStatusCode(500)
                    .withBody("{\"error\":\"" + e.getMessage() + "\"}");
        }
    }
}
```

Uses `java.net.http.HttpClient` (built into Java 11+) — the javaagent auto-instruments this via bytecode modification, producing HTTP client spans without any code changes.

#### 1.4 Create Java Handler: Mission Lambda (javawrapper)

**File**: `mission/src/main/java/com/example/mission/ControlMissionHandler.java` (new)

```java
package com.example.mission;

import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import com.amazonaws.services.lambda.runtime.events.APIGatewayProxyRequestEvent;
import com.amazonaws.services.lambda.runtime.events.APIGatewayProxyResponseEvent;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.node.ObjectNode;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.dynamodb.DynamoDbClient;
import software.amazon.awssdk.services.dynamodb.model.AttributeValue;
import software.amazon.awssdk.services.dynamodb.model.GetItemRequest;
import software.amazon.awssdk.services.dynamodb.model.GetItemResponse;
import software.amazon.awssdk.services.dynamodb.model.PutItemRequest;

import java.util.Map;

public class ControlMissionHandler implements RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> {

    private static final ObjectMapper mapper = new ObjectMapper();
    private static final DynamoDbClient dynamoDb = DynamoDbClient.builder()
            .region(Region.EU_CENTRAL_1)
            .build();

    @Override
    public APIGatewayProxyResponseEvent handleRequest(APIGatewayProxyRequestEvent event, Context context) {
        try {
            String rocketName = event.getPathParameters().get("rocketName");
            if (rocketName == null) {
                throw new IllegalArgumentException("No rocket name specified");
            }

            GetItemResponse response = dynamoDb.getItem(GetItemRequest.builder()
                    .tableName("Mission")
                    .key(Map.of("RocketName", AttributeValue.builder().s(rocketName).build()))
                    .build());

            if (!response.hasItem() || response.item().isEmpty()) {
                dynamoDb.putItem(PutItemRequest.builder()
                        .tableName("Mission")
                        .item(Map.of(
                                "RocketName", AttributeValue.builder().s(rocketName).build(),
                                "Destination", AttributeValue.builder().s("Mars").build(),
                                "Progress", AttributeValue.builder().n("0").build()
                        ))
                        .build());
            }

            ObjectNode result = mapper.createObjectNode();
            result.put("destination", "Mars");
            result.put("progress", 10);

            return new APIGatewayProxyResponseEvent()
                    .withStatusCode(200)
                    .withBody(mapper.writeValueAsString(result));
        } catch (Exception e) {
            return new APIGatewayProxyResponseEvent()
                    .withStatusCode(500)
                    .withBody("{\"error\":\"" + e.getMessage() + "\"}");
        }
    }
}
```

Uses AWS SDK v2 `DynamoDbClient` — the javawrapper layer auto-instruments this via `AutoconfiguredTracingExecutionInterceptor` SPI, producing DynamoDB spans without any code changes.

## Phase 2: Layer Acquisition (USER ACTION)

### Overview
The user builds (or downloads) the two Java OTel instrumentation layer ZIPs and places them at the project root.

### Required Files:

| File | Source | Purpose |
|---|---|---|
| `opentelemetry-javaagent-layer.zip` | Built from `opentelemetry-lambda/java/layer-javaagent` | Bytecode auto-instrumentation agent for Launch Lambda |
| `opentelemetry-javawrapper-layer.zip` | Built from `opentelemetry-lambda/java/layer-wrapper` | Handler substitution wrapper for Mission Lambda |

Both must be built for **arm64** architecture.

### What Each Layer Contains:

**javaagent layer:**
- `/opt/opentelemetry-javaagent.jar` — the bytecode agent
- `/opt/otel-handler` — wrapper script that sets `JAVA_TOOL_OPTIONS=-javaagent:/opt/opentelemetry-javaagent.jar`
- `/opt/extensions/` — OTel Collector Lambda Extension

**javawrapper layer:**
- `/opt/java/lib/` — OTel SDK + Lambda instrumentation JARs (added to classpath)
- `/opt/otel-handler` — wrapper script for plain `RequestHandler`
- `/opt/otel-proxy-handler` — wrapper script for API Gateway v1 with HTTP header context propagation
- `/opt/extensions/` — OTel Collector Lambda Extension

### Important Note on Collector Sidecar

Both Java layers bundle their own OTel Collector Lambda Extension at `/opt/extensions/`. This is the same collector that the standalone `opentelemetry-collector-layer-arm64.zip` provides. Having both layers attached means **two collectors would run simultaneously**, which is wasteful and may cause port conflicts (both try to listen on `localhost:4318`).

**Decision needed during implementation**: Either:
- **(a)** Remove the `collector_layer_arn` from both lambda module invocations (rely on the collector bundled in the Java layers), OR
- **(b)** Build the Java layers WITHOUT the bundled collector extension and continue using the standalone collector layer, OR
- **(c)** Keep both attached and verify whether the Lambda runtime handles the conflict gracefully (the Java layer's collector may take precedence)

The simplest approach is **(a)** — remove the standalone collector layer since the Java instrumentation layers already include it. This also means the `OPENTELEMETRY_COLLECTOR_CONFIG_URI` must point to a location the bundled collector can access, which is still `/var/task/collector.yaml` (bundled in the deployment ZIP).

**If the Java layers you build do NOT include a bundled collector**, keep the standalone collector layer attached.

   - Child span: HTTP GET to Mission Control API (auto-instrumented `java.net.http.HttpClient`)
   - The HTTP span should show the target URL, status code, and timing

2. **Mission Lambda trace** (javawrapper):
   - Root span: Lambda invocation (should be a child of the Launch Lambda's HTTP span via context propagation)
   - Child spans: DynamoDB GetItem and/or PutItem (auto-instrumented AWS SDK v2 via SPI)

3. **Distributed trace linking**:
   - Launch and Mission spans share the same trace ID
   - Mission's root span has Launch's HTTP client span as parent

## Testing Strategy

### Smoke Test:
- Single `curl POST /launch` — exercises the full call chain: Launch → HTTP → API Gateway → Mission → DynamoDB
- Run multiple times to observe both cold start and warm invocation behavior

### Trace Verification:
- Verify trace structure in observability backend
- Compare javaagent spans (HTTP client) vs javawrapper spans (DynamoDB) — both should show operation details (URL, table name, status codes)

### Edge Cases:
- First invocation creates DynamoDB item (PutItem span should appear)
- Subsequent invocations read existing item (only GetItem span)
- Missing `rocketName` in path should return 500 with error message

## Performance Considerations

- **Java cold starts** are significantly longer than Node.js. The javaagent adds 10-20s of bytecode scanning overhead on first invocation. `OTEL_JAVA_AGENT_FAST_STARTUP_ENABLED=true` mitigates this partially.
- **Memory**: Launch Lambda is set to 1024MB (more CPU for javaagent init), Mission Lambda uses default 512MB. Adjust based on observed cold start times.
- **Timeout**: Module defaults to 60s (up from 20s). Should be sufficient for cold starts.
- The javawrapper approach has notably lower cold start overhead (5-10s) since it uses handler substitution rather than bytecode scanning.
